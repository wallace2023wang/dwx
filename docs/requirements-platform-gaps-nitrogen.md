## 1. R1 —— RES 支持 `rule-group` 步骤类型（P0，已修复待补测试）

### 1.1 现状

- **设计期**：`shared/assets.js` 的 `flowSnapshot()` 会把 `rule-group` 步骤的成员规则合成为**完整 DRL** 写进步骤的 `drl` 字段（实测 4986 字符，含全部 11 条规则）。
- **编译期**：规则流 `compile` 通过；Release 创建时的编译门禁通过；质量门禁 19/19 通过。
- **部署期**：`POST /releases/:id/deploy` 返回 **400 `发布包步骤类型无效`**。

根因（`res/src/main/java/workbench/res/ResServer.java`）：

```java
if (!List.of("rule", "table").contains(step.path("type").asText())) return "发布包步骤类型无效";
```

`rule-group` 未被列入允许集合。

### 1.2 影响面

**任何使用 Rule Group 的规则流都无法发布上线**。这是设计文档 `ruleflow-editor-design.md` §3 明确支持的一等步骤类型，属于"设计期/编译期支持、运行期不支持"的能力缺口。

### 1.3 需求描述

1. RES 允许 `rule-group` 步骤类型；其执行语义与 `rule`/`table` **完全相同**（都已带完整 DRL，无需特殊处理）。
2. `validStepMappings()`、DRL 长度与总量校验对 `rule-group` 同样生效。
3. 发布包 schema 不因该改动而升版（向后兼容：旧 RES 仍可部署 `rule`/`table` 发布包）。

### 1.4 当前修复（临时）

已把 `"rule-group"` 加入允许列表并重建 RES 镜像，**实测部署成功**。但**缺少自动化测试**，存在回归风险。

### 1.5 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| A1 | 含 `rule-group` 步骤的 Release 可部署到 RES | `POST /deploy` 返回 2xx |
| A2 | 部署后 `/execute` 能正确执行规则组成员规则 | 返回预期 `facts` 与 `fired` |
| A3 | `rule`/`table` 步骤回归不受影响 | 既有 rules 项目全链路测试通过 |
| A4 | 步骤字段映射校验对 `rule-group` 生效 | 非法 mapping 仍返回 400 |
| A5 | 回归测试落地 | `res` 侧新增"rule-group 部署 + 执行"用例 |

## 2. R2 —— 废弃资产的归档语义（P0，待实现）

### 2.1 现状

本轮出现两个必须"退役但保留历史"的资产：早期设计产出的决策表「充氮状态迁移表」「充氮结束处理表」。
它们被新的 BAL 规则方案取代，但它们的版本历史仍被既有 Release 引用，**不能物理删除**。

现有手段都无法正确表达"已废弃"：

| 手段 | 结果 | 问题 |
|---|---|---|
| `DELETE /rules/:id`（软删除，`archived=true`） | 列表不再返回 | ① 资产在规则包树里消失，历史 Release 找不到它的归属；② 见 R8，**归档不解除包归属**，仍会被 Rule Group 拉进来编译 |
| 改 `category` 移出规则包 | 移出成功 | **状态被打回 `draft`**，列表显示为草稿，与"已废弃但历史有效"的事实不符 |

实测：改 `category` 后资产列表显示 `draft`，而版本历史（v3）仍在、既有 Release 仍可追溯。

### 2.2 根因

平台的资产状态机只有 `draft / in-review / published / archived` 四态，**缺少"已废弃（deprecated）"**这一显式语义：

- `published` = 可用且被引用；
- `archived` = 不再出现在列表，但**不表达"历史上曾发布、现已被取代"**；
- 改 `category` 是副作用路径，会触发 `advanceAssetRevision(item, 'saved')` 并重置发布态。

### 2.3 需求描述

引入**废弃（deprecated）**语义，与归档（archived）分离：

| 行为 | 归档 archived | 废弃 deprecated（新增） |
|---|---|---|
| 出现在默认资产列表 | 否 | 是（折叠区/灰显 + 徽标，可筛选） |
| 可编辑 | 否 | 否 |
| 可被规则流/Rule Group 引用 | 否 | **否**（关键：从包成员解析中排除） |
| 保留在规则包树中 | 否 | **是**（历史 Release 可追溯到归属包） |
| 版本历史与既有 Release | 保留 | 保留 |
| 状态显示 | `已归档` | `已废弃`（含"被谁取代"的可选说明） |

操作入口：资产列表右键菜单新增「标记为废弃」，需二次确认并显示"将被排除出规则包成员"。

### 2.4 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| B1 | 标记废弃后状态显示为「已废弃」而非「草稿」 | 列表状态列正确 |
| B2 | 废弃资产**不再**被 Rule Group / 规则流解析为成员 | 规则流编译不含其 DRL；无 BOM 版本过期报错 |
| B3 | 废弃资产仍出现在规则包树中（可追溯） | 包树节点可见，带废弃徽标 |
| B4 | 废弃资产不可编辑、不可再次发布 | 编辑入口禁用；`PUT`/`publish` 返回 409 |
| B5 | 既有 Release 部署与执行不受影响 | 旧 Release `/execute` 正常 |
| B6 | 可恢复：从废弃恢复到草稿（需权限） | 恢复后 `draft`，可重新编辑发布 |
| B7 | 审计事件记录废弃操作 | 含操作人、原因、被取代者 |

## 3. R3 —— 决策表条件支持字段引用（P1，待评估）

### 3.1 现状

平台的 BAL 规则已支持**声明式字段引用**（`valueSource: "field"` + `valueField`），生成 `RuleInput( nitrogenPct >= maxPct )`：

```js
// shared/rules.js:257
const constraint = item.valueSource === 'field' ? fieldConstraint(item, field) : literalConstraint(item, field);
```

但**决策表完全没有该能力**（`shared/assets.js` 中无任何 `valueSource` 处理）。决策表条件单元格只能是字面量：

```js
// shared/assets.js:134 → shared/rules.js:44
const v = formatDrlValue(field, operand);  // Double 要求 Number.isFinite(Number(operand))
// 写 "maxPct" → 抛"条件值无效"
```

### 3.2 影响面

"阈值/参数与实测值比较"是规则里的常见形态（浓度、温度、水位、信用分…）。用决策表表达时**只能写死字面量**，导致：

- 阈值随 Release 冻结，**改一个阈值就要重新发布 + 重新部署**；
- 想支持多仓/多设备不同阈值，只能"一个参数组合一个 Release"或改用 BAL。

本轮充氮的阈值判定因此**不得不放弃决策表**（业务可读性下降），是本项目最实质的建模能力缺口。

### 3.3 需求描述

决策表条件单元格支持引用同类型输入字段，与 BAL 的能力对齐：

- 单元格语法扩展，例如 `>=${maxPct}` 或列配置增加"比较值来源：固定值 / 业务字段"；
- 校验规则与 BAL 一致：须为 input 字段、同语义类型、不得自比较、运算符受类型约束（数值支持 `== != > < >= <=`）；
- 生成 DRL 与 BAL 相同：`field <op> valueField`（右侧不加引号）；
- 决策表行冲突/覆盖分析需感知"引用字段"形式的条件（保守处理为 `unknown` 而非误判重叠）。

### 3.4 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| C1 | 决策表单元格可写字段引用并生成 `a >= b` | 编译通过，DRL 形态正确 |
| C2 | 类型不一致 / 自比较被拒绝并给出明确文案 | 返回 400 |
| C3 | 字段引用条件与字面量条件可混用 | 同一张表内均生效 |
| C4 | 前端决策表编辑器提供"比较值来源"选择 | 与 BAL 编辑器交互一致 |
| C5 | 覆盖分析与诊断不误报 | 引用字段条件按 `unknown` 处理，不产生假重叠 |
| C6 | 既有决策表（纯字面量）零回归 | 全部既有套件通过 |

## 4. R4 —— 规则间传递中间判定结果的机制（P1，待评估）

### 4.1 现状

- 动作校验**只允许写 output 字段**：给 input 字段赋值返回 `动作字段无效或重复`（`shared/rules.js:86`）。
- 因此规则无法把自己算出的中间结论（如"浓度已达最大"）写回事实，供后续规则读取。
- 同一轮内规则**无法串接**：`启动充氮` 只写 `nextPhase`、不改 `phase`，所以同一轮里 `phase == "FILLING"` 的规则不可能命中。

实测：单次 `/execute` 只推进一个阶段（`fired` 仅 1 条），需要调用方**执行到不动点**补偿：

```
for round in 1..N:
    out = execute(facts)
    if out.nextPhase == facts.phase: break
    facts.phase = out.nextPhase
```

### 4.2 影响面

所有"分步判定 + 状态推进"的规则集都要在**每个调用方**重复实现不动点循环。本项目已在 `demo/control-loop.js` 实现；换一个集成方就要再写一遍，且容易漏（漏了会多下一次设备指令）。

### 4.3 需求描述（三选一，需评审）

| 方案 | 说明 | 代价 |
|---|---|---|
| **D-a（推荐）** | 平台侧提供"执行到不动点"语义：`/execute` 增加 `settle: true` 或 `maxRounds`，返回 `rounds[]` 轨迹 | 引擎侧改动小；调用方统一简化 |
| D-b | 允许动作写 input 字段（带类型校验） | 语义变复杂：input 既是"输入"又是"中间变量"，BOM 语义被污染 |
| D-c | 保持现状，把不动点循环写入集成规范与 SDK | 零平台改动；但每个集成方各自实现，易漏 |

### 4.4 验收标准（按 D-a）

| # | 验收项 | 判定 |
|---|---|---|
| D1 | `/execute` 支持 `settle`/`maxRounds`，返回逐轮轨迹 | 响应含 `rounds[]` |
| D2 | 存在循环规则时在 `maxRounds` 内终止，不无限循环 | 有硬上限并返回 `limitReached` |
| D3 | 默认行为不变（不传 `settle` 时单轮） | 既有调用零回归 |
| D4 | 轨迹可用于审计与调试 | 每轮含 `phase`、`fired`、`nextPhase` |

## 5. R5 —— 未赋值 Boolean 的"未传 vs false"语义（P1，待决策）

### 5.1 现状

实测（真实 Drools）：

| 写法 | 结果 |
|---|---|
| `RuleInput( nitrogenPct >= maxPct )` | ✅ 命中 |
| `RuleInput( pctAtLeastMax == null, ... )` | ❌ **永不命中** |
| `RuleInput( ... , pctAtLeastMax == null )` | ❌ **永不命中** |

原因：未赋值的 Boolean 字段被引擎按类型默认成 `false`，`== null` 永不成立。

### 5.2 影响面

规则无法区分"调用方漏传了这个信号"与"调用方明确传了 false"。对安全类规则尤其危险：漏传 `endReached` 会被当成"未到结束时间"，**该结束不结束**。
（注：平台此前已有记录 —— `platform-issues-and-fixes.md` §8.1/§8.2 的 `0/false` 默认值问题，本次是同一根因的另一种表现。）

### 5.3 需求描述（三选一，需评审）

| 方案 | 说明 |
|---|---|
| **E-a（推荐）** | 未赋值保持真正的 `null`（不默认成 `false`/`0`），让 `== null` 可用于守卫；同时 Team Server 侧对 `required` 字段继续硬校验 |
| E-b | 保持默认值，但 **RES 拒绝缺必填字段**（把 `required` 校验下沉到引擎，与 Team Server 对齐） |
| E-c | 保持不变，文档明确"未传即 false/0"，要求调用方自行保证完整性 |

> 现状是 E-c 的隐式行为 + 调用方自行补偿（本项目在驱动里做了 C1 必传字段断言）。建议至少做到 E-b。

### 5.4 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| E1 | 缺必填字段时 RES 返回明确错误（而非静默默认） | 400 + 缺失字段名 |
| E2 | 可选字段的"未传"与"传 false"可区分 | 规则可用守卫区分 |
| E3 | 既有规则/套件回归不受影响 | 全量测试通过 |
| E4 | 错误文案说明"缺哪个字段、该字段是否必填" | 文案含字段名 |

## 7. R7 —— 资产详情返回产物冻结的 BOM 版本（P1，已修复）

### 7.1 现状与根因

平台**有意要求**：BOM 升版后，依赖它的已发布资产必须重新发布，否则规则流拒绝编译：

```
充氮结束处理表 使用 BOM v4，当前为 v6，请先重新发布该资产
```

但 `projectAssetDetail` **原先不返回**该资产产物冻结的 BOM 版本，调用方无法判断"是否需要重发"——只能靠"先编译、失败、再解析错误文案、再重发"的试错流程。

### 7.2 当前修复（已实现）

`server/index.js` 的 `projectAssetDetail` 增加：

```js
versions: (item.versions || []).map(v => ({ number, createdAt, bomVersion, engineVersion })),
publishedBomVersion: item.versions?.at(-1)?.bomVersion ?? null,
```

### 7.3 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| G1 | 资产详情返回 `publishedBomVersion` | 字段存在且值正确 |
| G2 | 返回 `versions[]`（含各版本 `bomVersion`） | 可追溯历史 |
| G3 | 前端资产详情展示"产物冻结 BOM 版本"与过期提示 | 页面可见 |
| G4 | 调用方可据此自动判断重发 | 集成脚本不再依赖错误文案 |

## 8. R8 —— 归档资产应解除包归属（P1，待实现）

### 8.1 现状

资产归档（`archived=true`）后：

- 资产列表不再返回它；
- **但它仍带 `category`，因此仍被规则包成员解析命中** —— 规则流编译时报"使用 BOM vN"这类与已归档资产有关的错误（本项目实测到：「充氮结束处理表」归档后仍被规则流引用报 BOM 版本过期）。

### 8.2 需求描述

归档资产在**包成员解析**（`resolveRuleGroupMembers`、规则流步骤引用、包树统计）中一律排除；归档不改变 `category` 值（保留可追溯性），但解析时按 `archived` 过滤。

### 8.3 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| H1 | 归档资产不出现在规则包成员解析结果中 | 规则流编译不涉及它 |
| H2 | 归档资产仍可在"已归档"筛选中查到、`category` 保留 | 可追溯 |
| H3 | 归档资产不影响包树计数 | 包资产数不含已归档 |

## 9. R9 —— BAL 编辑器支持 `raw` 条件（P1，已修复）

### 9.1 现状（修复前）

`frontend/src/components/assets/BalRuleView.tsx` 的 `validateBalDraft` 只处理 `{field, operator, value}` 形态：

```ts
const field = fields.find(c => c.key === condition.field && c.direction === 'input')
if (!field) issues.push(`第 ${index + 1} 个条件引用的 BOM 字段不存在`)
const error = valueError(condition.value, field)   // field undefined → 再报一次
```

而平台**后端支持 `raw` 条件**（`shared/rules.js:75` 显式 `continue` 跳过校验，`:144` 原样拼进 `RuleInput(...)`）。
于是**一条合法且能正确执行的规则**在编辑器里显示为"字段已失效"并产生成对报错。
（更早的 `project-93d1309c` 里就存在只有 `raw` 的条件，同样受影响，属长期存在。）

### 9.2 当前修复（已实现）

编辑器新增 `isRawCondition()`（`BalRuleView.tsx:170`）与内联/独立 DRL 徽标渲染，`raw` 条件不再走字段校验。

### 9.3 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| I1 | `raw` / `pattern` 条件正常渲染，不报"字段已失效" | 编辑器无红框 |
| I2 | `validateBalDraft` 跳过 `raw` 条件（与后端一致） | 无成对报错 |
| I3 | `raw` 条件保存后原样保留 | 往返不丢语义 |
| I4 | 历史含 `raw` 的规则打开无告警 | 回归 |

## 11. 实施建议顺序

| 顺序 | 内容 | 理由 |
|---|---|---|
| 1 | **R1 补回归测试** | 修复是临时加的，无测试护城河；Rule Group 一旦回归，所有用它的规则流都无法上线 |
| 2 | **R2 废弃语义** | 目前靠"改 category"这种副作用路径绕过，状态语义已失真；每个规则集退役时都会遇到 |
| 3 | **R8 归档解除包归属** | 与 R2 同族、改动小，能立即消除"归档资产仍被编译"的坑 |
| 4 | **R5 必填字段下沉校验** | 安全类规则的静默默认值风险最高（该结束不结束） |
| 5 | **R4 执行到不动点** | 统一各集成方的补偿实现，避免漏做 |
| 6 | **R3 决策表字段引用** | 能力缺口最大但改动最大，建议单独立项评估 |
| 7 | R6 / R7 前端展示 / R10 | 文档与体验收尾 |

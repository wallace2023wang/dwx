# 自动充氮控制 —— 落地方案选型（3 条路线）

> 版本：v1.1 ｜ 状态：**已选型**（2026-10-02 定：路线 A′ + C；落地设计见 `nitrogen-auto-fill-asset-design.md`）｜ 日期：2026-10-02
> 关联：`dual-engine-architecture-design.md`、`ruleflow-editor-design.md`、`decision-table-design.md`、`cep-time-driven-statement-support.md`、`platform-issues-and-fixes.md`
> 说明：本文给**架构选型**，不给实现步骤；三条路线在"状态存哪、谁计时、契约面多宽"上根本不同，不宜混做。

---

## 0. 先看决定性的 4 个取舍点

任何方案都逃不掉这 4 个问题。它们定完，方案基本就唯一了。

| 取舍点 | 选项 | 影响 |
|---|---|---|
| **D1 状态存哪** | ① 仓端中控（PLC/DCS） ② 平台 ③ 引擎运行时内存 | 决定重启安全性、审计能力、平台改动量 |
| **D2 谁计时** | ① 仓端中控 ② 平台调度器 ③ 引擎 timer | 决定"暂停/继续"的实现难度（暂停=冻结计时） |
| **D3 契约面多宽** | ① 只做"状态机函数" ② 做"实例生命周期" ③ 做"事件协议" | 决定平台是规则工厂还是运行时 |
| **D4 浓度怎么进来** | ① 每分钟拉 ② 变化即推 ③ 周期事件流 | 决定断流/越限等安全行为落点 |

客户需求里最容易和实现打架的是 D2：**"环流 4 小时"和"暂停后可继续"必须一起看**。暂停期间计时必须冻结，所以计时器不能是"发起后 N 小时"的一次性闹钟，必须是**由状态驱动的累计量**。这一条把"引擎 timer 直接搞定"的幻想排除掉了。

---

## 1. 路线 A：状态机即服务（平台只产"纯函数"）

**定位**：平台不引入任何运行时新概念。充氮任务的全部运行状态放在**已有的仓端中控**里（那里本来就有 PLC/DCS、有设备状态、有传感器），平台负责让这份判定逻辑**可信、可版本化、可门禁、可审计**。

```
仓端中控（状态持有者 + 计时器）
  │
  │ 每 1 分钟：组装当前快照 facts
  │  { phase, nitrogenPct, maxPct, minPct, circElapsed, endReached, paused }
  ▼
RES / Drools（纯函数，无状态）
  │  POST /api/projects/:id/releases/:rid/execute  { facts }
  ▼
输出 { nextPhase, genCmd, fillValveCmd, circValveCmd, fanCmd, reason }
  │
  └─ 中控写回本地状态 → 下发设备指令 → 下一分钟
```

### 1.1 平台交付物

| 资产 | 内容 |
|---|---|
| BOM | `NitrogenControl`（入参，含 `endReached`/`paused` 布尔信号）+ `NitrogenCommand`（出参） |
| 规则包 `nitrogen-control` | 7 条迁移规则（决策表或 BAL），salience 从低到高：启动/充氮达标/环流期满/保氮过低/补氮达标/结束完成/暂停全关 |
| 测试套件 | 每次迁移一个用例 + 完整环路回放用例（见 §5） |
| Release | 不可变 + checksum + 套件门禁；中控按 Release ID 执行，升级靠新 Release |

### 1.2 变体 A′（推荐先做）：把 7 条规则收成**一张决策表**

同一个状态机其实是一张**状态迁移表**，用 `decision-table` 表达比 7 条 BAL 更贴业务、更好评审：

| # | phase | endReached | paused | nitrogenPct | → nextPhase | 制氮机 | 充氮阀 | 环流阀 | 风机 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | PENDING | | false | | FILLING | ON | OPEN | CLOSED | ON |
| 2 | FILLING | | false | `>=${maxPct}` | CIRCULATION | OFF | CLOSED | OPEN | ON |
| 3 | CIRCULATION | | false | `circElapsed=true` | HOLDING | OFF | CLOSED | CLOSED | OFF |
| 4 | HOLDING | | false | `<${minPct}` | REPLENISHING | ON | OPEN | CLOSED | OFF |
| 5 | REPLENISHING | | false | `>=${maxPct}` | CIRCULATION | OFF | CLOSED | OPEN | ON |
| 6 | *(任意)* | true | | | COMPLETED | OFF | CLOSED | CLOSED | OFF |
| 7 | *(任意)* | | true | | *(保持)* / PAUSED | OFF | CLOSED | CLOSED | OFF |

**为什么这样排**：平台决策表是确定性"后写覆盖"语义（`platform-issues-and-fixes.md` §2.5），**行序即优先级**。把"结束"和"暂停"放最后，就天然实现了客户要求的"任何阶段都能暂停/结束"。行 1–5 的 phase 条件互斥，不会互抢。

**唯一需要平台确认的能力点**：第 2/4/5 行的阈值能否写成 `>=${maxPct}` 这类**引用字段值**而非字面量。现有决策表支持内联比较符（`<0.8`、`>=25`）和区间，但**引用另一个字段作为比较值**需要核实（这是本路线唯一的平台验证项；不支持则退回 7 条 BAL 的 `raw` 条件写法——已实测可编译）。

**这条变体的额外收益**：一张表就是一份可交给客户签字确认的状态迁移规格，业务人员能直接读；测试可以用行覆盖率断言（决策表行覆盖率已在平台测试套件里支持）。

### 1.3 交付边界与责任

| 谁 | 负责什么 |
|---|---|
| 平台 | 状态机逻辑、参数化阈值、版本冻结、编译门禁、测试回归、变更审计、报告 |
| 中控（客户/集成商） | 持有 `phase` / `circAccumMs` / 暂停点；每分钟调用一次；以"调用失败 → 关阀"为默认安全态 |
| 明确不做 | 平台不保存任何运行业务实例；平台不知道某个仓现在处于哪个阶段 |

### 1.4 这个路线的短板（必须写进合同）

1. **平台侧不可观测**：出问题时平台只能看到"某一分钟收到过什么 facts、返回过什么"，无法还原阶段时间线。
2. **安全兜底在中控**：如果中控不按时调用，平台不会、也无法强制关阀。必须要求中控侧实现**心跳失败即关充氮阀**。
3. **暂停语义由中控保证**：平台只拿到 `paused=true/false`，暂停期间不调用即可。

## 2. 路线 B：平台托管执行外壳（会话/实例 + 调度器）

**定位**：平台从"规则工厂"升级为"能托管长时任务"的执行面。状态、计时、指令下发全部由平台负责，中控退化为纯设备网关。

```
Team Server（治理 + 实例 + 调度器）
  │  每 1 分钟 tick 一次
  │  读浓度（拉/推）→ 组装 facts → RES 执行 → 落库状态 → 推送指令
  ▼
RES（纯判定，一次一轮）        webhook → 中控 → 设备 + 回执
```

### 2.1 与路线 A 的本质差别

| 维度 | A | B |
|---|---|---|
| 平台是否新增领域对象 | 否 | 是：**执行实例**（阶段、参数、暂停点、累计时长、指令流水） |
| 平台是否新增调度 | 否 | 是：周期驱动器（含重启恢复、幂等、互斥断言） |
| 平台是否下发设备指令 | 否 | 是：webhook + 幂等键 + 回执 + 重试 |
| 可观测性 | 低 | 高（阶段时间线、指令审计、异常重放） |
| 交付周期 | 短 | 长（实例模型 + 调度 + 指令契约 + 前端页面） |
| 客服成本 | 中（问题在客户侧） | 低（平台能看到全链路） |

### 2.2 这个路线的真实风险清单

1. **一次执行不等于一轮决策**：RES 单次求解只跑一轮，`FILLING→CIRCULATION` 后不会自动算出环流期设备指令。若直接取输出下发，会开出错误阀门。驱动器必须"执行到不动点"（最多 3 轮，phase 不再变化即停）。
2. **必须做成通用能力才值得做**：如果只为充氮加一套实例与调度，第二个长时场景（通风降温、气调、熏蒸、烘干）来了要重写一遍。做成通用"决策计划实例"才能摊薄成本。
3. **多副本部署**：调度必须单飞（PG advisory lock 或分片），否则一个实例被两个进程推进，设备指令会抖。
4. **暂停期间不决策**：实例要从扫描队列摘除，否则暂停时浓度变化仍会触发迁移。

## 3. 路线 C：事件化阶段迁移（CEP 引擎承载迁移，不承载时长）

**定位**：把"阶段迁移"建模为**事件**而不是"状态读取+判定"。每次迁移 `insert` 一条带时间戳的阶段事件；"当前阶段"= 最近一条阶段事件；"环流满 4 小时"= 在最近环流事件之后 N 时间无新事件。这是与 A/B 完全不同的建模方式（状态内生于事件流，而非保存在某个实例字段里）。

```
浓度采样事件 ──┐
              ├─► Esper 事件流（每次采样即判定）
阶段事件      ──┘     ├─ "当前阶段=FILLING 且 pct>=max" → insert 阶段事件 CIRCULATION
（自引用）             ├─ pattern[every CIRCULATION → timer:interval(4h)] → HOLDING
                      └─ "当前阶段=HOLDING 且 pct<min" → REPLENISHING
                            │
                            └─ 部署级 listener → webhook（阶段事件 + 建议设备指令）
```

### 3.1 已具备的能力（本项目实测过）

`cep-time-driven-statement-support.md` 已落地：pattern/timer 语句可校验、可真实编译、可执行；部署级 listener 能在请求结束后继续捕获 timer 输出并 webhook 推送。现网 `project-7c12c971` 已有 3 条阶段迁移语句（演示节奏 20 秒）。

### 3.2 这条路线的硬伤

| 问题 | 说明 |
|---|---|
| **暂停=重置计时** | 暂停期间"环流计时必须冻结"，而 timer 一旦启动无法暂停。只能把暂停建模成"新的阶段事件 + 恢复时重新开始计时"，**语义上是重置而非续算**——与客户"暂停后可继续"的直觉不符（除非客户接受"暂停后环流重新计 4 小时"） |
| **状态在内存、重启即丢** | Esper 无内置持久化（`dual-engine-architecture.md` §1.4 已标为已知软肋），进程重启后"当前阶段"丢失，可能重复开阀 |
| **结束时间无法表达** | `timer` 只能表达"某事件后 N 时间"，表达不了"到 `endAt` 结束"。仍需外部定时注入"结束事件" |
| **设备指令语义弱** | 引擎输出的是"检测事件"，幂等/互斥/回执要靠消费侧补，等于把 B 的复杂度挪到消费侧 |
| **可治理性差** | 迁移逻辑散在 EPL 里，业务人员读不懂，状态迁移规格无法直接签字确认 |

**结论**：路线 C 适合"事件天然存在且状态可重算"的场景（如从 Kafka 流里持续判定工况），**不适合**"有一个必须持久化、可暂停、有明确起止时间"的任务实例。它在本需求里最合适的位置是**安全告警通道**（浓度越上限/断流检测 → 强制关充氮设备），而不是控制主链路。

## 4. 三条路线对照

| 维度 | A 状态机即服务 | A′ 决策表变体 | B 平台托管实例 | C 事件化迁移 |
|---|---|---|---|---|
| 状态存哪 | 中控 | 中控 | 平台 | 引擎内存 |
| 谁计时 | 中控 | 中控 | 平台调度器 | 引擎 timer（不可暂停） |
| 平台改动 | **零** | 零（1 项能力核实） | 大（实例+调度+指令+UI） | 中（EPL + 消费侧） |
| 暂停/继续 | 天然（不调用即暂停） | 天然 | 需实例状态机 | 语义退化 |
| 重启安全 | 依赖中控 | 依赖中控 | 平台保证 | 差 |
| 可审计 | 只到调用级 | 只到调用级 | 全链路 | 事件级 |
| 业务可读性 | 中 | **高（一张表）** | 中 | 低 |
| 交付周期 | 1–2 周 | 1–2 周 | 5–8 周 | 3–4 周 |
| 适合当平台产品 | 弱 | 弱 | **强** | 中 |

## 5. 无论选哪条，都必须一起定死的 3 份契约

这三份与路线无关，建议先冻结，否则任何路线的实现都会各写一套。

### 5.1 状态机契约（客户的"规则"翻译成可签字规格）

| phase | nitrogenPct | circElapsed | endReached | paused | → nextPhase | 制氮机 | 充氮阀 | 环流阀 | 风机 |
|---|---|---|---|---|---|---|---|---|---|
| PENDING | — | — | false | false | FILLING | ON | OPEN | CLOSED | ON |
| FILLING | ≥ maxPct | — | false | false | CIRCULATION | OFF | CLOSED | OPEN | ON |
| CIRCULATION | — | **true** | false | false | HOLDING | OFF | CLOSED | CLOSED | OFF |
| HOLDING | < minPct | — | false | false | REPLENISHING | ON | OPEN | CLOSED | OFF |
| REPLENISHING | ≥ maxPct | — | false | false | CIRCULATION | OFF | CLOSED | OPEN | ON |
| 任意 | — | — | **true** | — | COMPLETED | OFF | CLOSED | CLOSED | OFF |
| 任意 | — | — | — | **true** | 保持当前阶段 | OFF | CLOSED | CLOSED | OFF |

固化的口径（需客户确认）：
- `endReached` 优先级最高（任何阶段到点即结束）；`paused` 次高。
- `≥ maxPct` 用闭区间（客户"大于最大"与"到达最大"两种说法统一）。

> 本表是"业务语义版"（便于客户签字）。**定稿实现版**见 `nitrogen-auto-fill-asset-design.md` §3：因决策表动作只能赋常量，暂停行输出 `PAUSED` 而非"保持当前阶段"，恢复时由中控回填。
- `HOLDING` 用严格 `< minPct`（客户明确说"小于最小"）。
- 环流计时**只累加运行中的时长**，暂停期间冻结（`circElapsed` 由调用方按此口径计算后传入）。

### 5.2 输入输出契约

- 输入必须是**自洽快照**：调用方一次传全（阶段、浓度、阈值、时间信号、暂停信号），平台不做跨调用状态推断。
- `now`/`endReached` 由调用方算好传入：平台不读系统时钟（否则测试无法回放，跨时区也会出错）。
- 输出必须**自描述**：`nextPhase` + 4 路设备指令 + `reason`（中文迁移原因，供审计与展示）。
- 浓度无效/断流必须显式传 `pctValid=false`，**不得用 0 或旧值代替**（否则会误触发补氮或误判达标）。

### 5.3 安全契约

| 场景 | 要求 |
|---|---|
| 平台/引擎不可达 | 默认安全态：关制氮机、关充氮阀（宁可不充，不可失控充） |
| 浓度越上限 | 独立通道强制关充氮设备，优先级高于状态机任何迁移 |
| 浓度数据超时 | 视同断流 → 保护性关闭 + 告警，不按旧值继续 |
| 充氮阀/环流阀互斥 | 输出前断言两者不可同时 OPEN；违反则拒绝下发并告警 |
| 指令幂等 | 指令键 `{taskId, tickSeq, phase}`；接收方去重；仅当阶段或设备态变化才下发 |
| 审计 | 每次迁移与指令都要有"谁、何时、什么输入、为什么"的留痕 |

## 6. 推荐组合

**默认推荐：路线 A′（决策表状态机）+ 路线 C 仅用于安全告警。**

- 控制主链路用**一张决策表**表达状态机：业务可读、可签字、可测、可版本化，平台零改动（除 1 项比较能力核实）。
- 计时与状态放仓端中控：那里本来就有设备状态和传感器，且暂停天然成立（不调用即暂停）。
- 安全告警（越上限/断流/补氮超时）用 **CEP 事件流**：这是它真正擅长的领域，且本项目已有落地经验。
- 职责边界干净：**平台保证"判得对 + 可追溯"，中控保证"跑得久 + 关得掉"**。

**什么情况下升级到路线 B**：
1. 客户不接受"状态在中控"，要求平台侧可观测、可接管、可远程暂停；
2. 同类长时任务场景 ≥ 3 个（通风降温、气调、熏蒸、烘干…），通用"决策计划实例"能摊薄成本；
3. 需要平台统一执行设备指令并留全链路审计（合规/验收要求）。

**不建议路线 C 做控制主链路**（原因见 §3.2），但它在告警通道上是正确选择。

### 6.1 补充：推荐组合是**双引擎、两套独立 BOM**

A′ + C 意味着同时使用 Drools 与 Esper，落地为**两个项目、两套互不共享的 BOM**：

| | 控制（A′） | 安全告警（C） |
|---|---|---|
| 引擎 / 项目 | Drools / 新建 `engine=rules` | Esper / 复用 `engine=cep` |
| BOM | 状态机入参与设备指令 | 传感器事件类型 |
| 资产 | 决策表 + 规则集 + 套件 | EventStream |

核实：平台 BOM 按项目隔离（`bom-<projectId>.json`，`server/index.js:40,131`），事件校验走 `validateEventPayloads(events, cepBom)`、控制执行走 `parseFacts(facts, rulesBom)`，**两引擎之间无共享字段定义、无交叉校验**。因此两套 BOM 可独立演进，改一边不需要重发另一边的 Release。

两者唯一连接点在**仓端中控**：把 CEP 侧的浓度原始值折算成 Drools 侧需要的布尔信号。详细契约（O1–O5）见 `nitrogen-auto-fill-asset-design.md` §1.1。

## 7. 待确认清单（选型前必须回答）

| # | 问题 | 为什么阻塞选型 |
|---|---|---|
| Q1 | 运行状态放在**仓端中控**还是**平台**？客户/集成商是否接受"平台不持有任务实例"？ | 直接决定 A 还是 B |
| Q2 | 暂停时设备是**全关**还是**保持密闭**？ | 决定暂停行怎么写、恢复时是否重开阀 |

# 规则参数化与运行期调参需求设计

> 版本：1.0 ｜ 状态：需求待评审 ｜ 日期：2026-10-02
> 来源：粮库自动充氮控制落地后，客户提出"最大/最小氮气浓度这几个判断参数会动态调整，应该在规则中实现，以便随时调整"
> 关联：`nitrogen-auto-fill-asset-design.md`、`requirements-platform-gaps-nitrogen.md`、`ruleflow-editor-design.md`、`bom-editor-design.md`
>
> 本文只写需求与验收标准，不含实现。开发任务由项目方排期。
> 每条需求标注 **责任方**（平台 / 项目侧）与 **状态**。

---

## 0. 需求总览

### 0.1 一句话需求

让"阈值类判定参数"成为**可管理、可校验、可在运行期调整**的规则输入，且规则本身不写死任何阈值数字。

### 0.2 已实现的部分（先明确边界，避免重复开发）

"规则里不写死阈值、改参数即改行为"**已经实现并实测通过**，形态如下：

```jsonc
// 规则条件：只出现变量名，没有任何数字
{ "field": "nitrogenPct", "operator": ">=", "valueSource": "field", "valueField": "maxPct", "value": "" }
// 生成 DRL：RuleInput( nitrogenPct >= maxPct )
```

实测证据（同一份已发布规则，仅改传入参数）：

| 传入阈值 | 起始浓度 | 实测结果 |
|---|---|---|
| `[90, 95]` | 94% | `FILLING`（未达上限，保持充氮）✅ |
| `[85, 93]` | 94% | `CIRCULATION`（94 ≥ 93，转环流）✅ |
| `[98, 99]` | 94% | `FILLING`（远离上限）✅ |
| `[85, 93]` | 93% | `CIRCULATION`（等于上限，含等号）✅ |

**结论：规则侧参数化已完成，无需开发。** 本需求的缺口在"参数怎么管、怎么改、安不安全"。

### 0.3 缺口清单

| 编号 | 需求 | 责任方 | 优先级 | 状态 |
|---|---|---|---|---|
| **P1** | 运行期调整参数（不重启任务、不重新发布规则） | 项目侧（标准契约）+ 平台（可选通用能力） | **P0** | ❌ 待开发 |
| **P2** | 参数安全语义与联锁可达性 | 项目侧（规则与配置） | **P0** | ❌ 待确认后开发 |
| **P3** | 参数的可管理性与校验（版本化、取值校验、审计） | 平台 | P1 | ❌ 待开发 |
| S1 | "零命中"兜底覆盖（`nextPhase == null`，依赖 R5 包装类型能力） | 项目侧（规则） | P1 | ❌ 待开发 |

## 1. P1 —— 运行期调整参数（P0）

### 1.1 现状

- **平台侧**：没有"任务/实例"概念，参数不属于任何平台对象；Release 不记录执行期参数；不存在调参接口。
  （实测：`server/index.js` 无 task/instance 相关模型，`shared/releases.js` 无 `params`。）
- **调用方（本项目 demo）**：阈值只能在**创建任务时**通过 `POST /api/start` 传入；任务启动后**没有任何调整入口**。

### 1.2 影响面

**这是本需求的核心缺口，且与客户原话直接冲突。** 客户要求"随时调整"，但当前状态下想改一个阈值必须：

```
结束当前任务 → 重新创建任务 → 重新走充氮/环流/保氮流程
```

代价不只是操作麻烦：**任务内的运行状态会全部丢失**——当前阶段、环流累计时长（4 小时）、暂停点、设备指令流水、审计轨迹都会重置。对一个已经环流 3 小时的任务来说，"改个阈值"等于让这 3 小时白跑。

### 1.3 需求描述

#### 1.3.1 契约要求（平台与调用方共同遵守）

1. **参数属于任务配置，不属于规则**：任务创建时确定一组参数；规则每次执行都从 facts 读取当前值。
2. **规则侧只引用参数名，不出现阈值数字**（已满足）。
3. 运行期更新参数后，**下一个决策周期立即按新参数判定**，不得要求重新发布规则或部署 Release。
4. 参数变更**不得重置**任务运行状态（阶段、环流累计、暂停点、指令流水均保留）。
5. 参数变更必须**留痕**：谁、何时、从什么值改到什么值、原因。

#### 1.3.2 平台侧可选通用能力（建议但非阻塞）

若平台希望把"运行期参数"提升为通用能力，建议提供：

| 能力 | 说明 |
|---|---|
| 参数集（Parameter Set）声明 | 项目级声明"本规则集接受哪些参数、类型、取值范围、默认值、是否必填" |
| 执行期参数回显 | `/execute` 响应中回显本次实际使用的参数，便于审计与复现 |
| 参数变更审计 | 参数版本化 + 变更事件进入审计日志 |

> 注意：**平台不要保存单个任务的运行状态**。状态归属调用方（见 `nitrogen-auto-fill-asset-design.md` §1.1 的双引擎与 BOM 隔离约定）。平台只提供"参数声明 + 校验 + 审计"，不承载实例。

#### 1.3.3 项目侧实现要求（demo / 中控适配器）

1. 新增运行期调参接口，语义为"更新当前任务的参数并立即生效"。
2. 参数校验：类型、范围（0–100）、`maxPct > minPct`；非法值拒绝且**不改变现有参数**。
3. 界面提供参数输入与"应用"入口，并显示当前生效值。
4. 调参后**不中断**决策循环，下一 tick 使用新值。

### 1.4 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| A1 | 任务运行中修改 `maxPct`，下一决策周期即按新值判定 | 实测行为随参数变化，无需重启任务 |
| A2 | 调参不重置运行状态 | 阶段、环流累计、暂停点、指令流水保持不变 |
| A3 | 调参不需要重新发布规则或部署 Release | Release ID 与 checksum 全程不变 |
| A4 | 非法参数被拒绝且不改动现有值 | 返回 400，原参数仍生效 |
| A5 | 参数变更留痕 | 记录操作人、时间、原值、新值、原因 |
| A6 | 暂停期间调参，恢复后按新参数生效 | 恢复后首个周期使用新值 |
| A7 | 边界：`maxPct == minPct`、越界值、非数值 | 均被拒绝并给出明确文案 |

## 2. P2 —— 参数安全语义与联锁可达性（P0）

### 2.1 现状与问题

当前实现里 `maxPct` 被当作**充氮目标**（达到即停止充氮），而**联锁值是另一个独立参数**：

```js
// 调用方驱动器
maxPct: 95,            // 达到 95% 停止充氮
safetyMaxPct: 99,      // 浓度 ≥ 99% 触发联锁、强制关充氮设备
const safetyTripped = pct >= safetyMaxPct;
```

**矛盾**：规则在 95% 就停止充氮，浓度在正常控制下**永远到不了 99%** → **安全联锁不可达**。
演示时该联锁只在"手工注入 99.5%"下才触发过，属于人为构造而非真实工况。

### 2.2 影响面

1. **安全功能形同虚设**：若发生传感器漂移、阀门卡滞、制氮机失控等异常，浓度持续上升时**没有任何规则或联锁会响应**——因为唯一能拦住它的那条判断永远不会满足。
2. **两个参数职责重叠且未定义**：`maxPct` 与 `safetyMaxPct` 谁是控制上限、谁是安全上限，文档与规则描述都没写清，后来人无法判断。

### 2.3 需求描述

**必须先由客户确认语义，再据此调整规则与配置。** 三种候选（三选一）：

| 方案 | 语义 | 规则/配置改动 |
|---|---|---|
| **甲** | `maxPct` = 充氮目标上限（保持现状）；`safetyMaxPct` 作为**独立安全上限**，必须**严格大于** `maxPct`（建议 `maxPct + 2` 起），且联锁条件独立于状态机 | 规则不动；配置强制约束 `safetyMaxPct > maxPct`，并在演示/文档中让联锁可达 |
| **乙** | `maxPct` 本身就是**安全上限**，不再需要独立联锁值；控制目标为维持在 `[minPct, maxPct]` 区间 | 去掉 `safetyMaxPct`；联锁语义并入规则（超上限即停并告警） |
| **丙** | "最大/最小"指**报警带**而非控制带（如最小=预警下限、最大=预警上限，控制另有目标值） | 需客户给出准确参数定义后重构 |

无论选哪个，都必须满足以下通用要求：

1. **联锁可达性**：安全联锁的触发阈必须处于正常工作范围**之上**，在真实工况下可被触发（不能像现在这样不可达）。
2. **联锁优先级最高**：联锁触发时强制关闭充氮设备，优先级高于状态机任何迁移；且**独立于**主状态机（即使状态机因故未推进，联锁仍生效）。
3. **参数间约束显式化**：如存在多档阈值（目标 / 预警 / 安全），其大小关系必须在参数校验阶段强制，非法组合直接拒绝。
4. **文档化**：每个参数的准确定义、单位、与其他参数的关系，必须写入规则描述与接口文档。

### 2.4 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| B1 | 客户确认的语义写入参数定义与规则描述 | 文档一致，无歧义 |
| B2 | 安全联锁在**真实工况**下可达（非仅靠手工注入） | 构造持续超限工况能触发联锁 |
| B3 | 联锁触发时充氮设备被强制关闭 | 设备指令为 `OFF`/`CLOSED` |
| B4 | 联锁独立于状态机：状态机不推进时联锁仍生效 | 构造状态机零命中场景，联锁仍动作 |
| B5 | 非法参数组合（如 `safetyMaxPct <= maxPct`）被拒绝 | 返回 400 + 明确文案 |
| B6 | 联锁触发与解除均留痕并入告警通道 | 审计记录 + 告警事件 |

## 3. P3 —— 参数的可管理性与校验（P1）

### 3.1 现状

- 参数**只存在于调用方代码的默认值**里（本项目 demo 中为 `maxPct: 95, minPct: 90`）。
- 平台侧**没有任何参数声明**：不知道某个规则集接受哪些参数、类型是什么、取值范围、是否必填。
- 因此参数写错（拼错 key、类型不对、越界）**只能在运行期由引擎报错或静默默认值兜底**，无法在发布前发现。

### 3.2 影响面

- 参数名/类型没有单一事实来源，规则、调用方、文档三处各写一份，容易漂移。
- 无法在 Release 发布前校验"调用方提供的参数是否满足该规则集要求"。
- 出现问题时无法回答"这次执行用的是哪组参数"（Release 不记录执行期参数）。

### 3.3 需求描述

| # | 能力 | 说明 |
|---|---|---|
| C1 | **参数声明** | 项目级声明本规则集接受的参数：名称、类型、取值范围、默认值、是否必填 |
| C2 | **发布前校验** | 发布/创建 Release 时校验规则引用的参数都在声明内；调用方提供的参数满足声明约束 |
| C3 | **执行期回显** | `/execute` 响应回显本次实际使用的参数，支持事后复现与审计 |
| C4 | **参数变更审计** | 参数变更作为审计事件记录（配合 P1 的留痕要求） |
| C5 | **规则编辑器联动** | BAL 编辑器的"业务字段"下拉在字段引用模式下，只列出**同类型且已声明为参数**的字段（或明确区分"数据字段 / 参数"） |

> **不在本期范围**：平台保存单个任务的运行状态或参数快照（状态归调用方）。

### 3.4 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| C1-1 | 可声明参数集并持久化 | 项目详情可查 |
| C1-2 | 引用未声明参数时给出警告 | 编辑器/发布校验提示 |
| C2-1 | 发布前能拦截"引用了不存在参数"的规则 | 发布被拒并给出参数名 |
| C2-2 | 调用方参数不满足声明约束时明确报错 | 返回 400 + 具体字段 |
| C3-1 | 执行响应含实际使用参数 | 字段可读且可复现 |
| C4-1 | 参数变更进入审计日志 | 含前后值与操作人 |
| C5-1 | 字段引用模式下下拉按类型过滤 | 只出现同类型候选 |

## 4. S1 —— "零命中"兜底覆盖（P1，项目侧）

> **前置能力已就绪**：`requirements-platform-gaps-nitrogen.md` R5 已修复——
> 新发布产物把数值/布尔字段生成为 **Java 包装类型**（`java.lang.Boolean` / `java.lang.Double`），
> **未赋值保持 `null`**。因此 `== null` 守卫现在可用（此前"未赋值被默认成 false，守卫永不成立"的结论已失效）。
>
> 实测证据（真实 Drools）：

| 输入 | 命中规则 | 输出 `nextPhase` |
|---|---|---|
| `phase = "FILLING"` | 正常迁移规则 | `CIRCULATION` |
| `phase = "PAUSED"`（无正常规则命中） | **兜底规则（`nextPhase == null`）** | 确定值（非空） |

### 4.1 现状问题

当前规则集所有迁移规则都带 `paused == false` 守卫。当传入 `phase = "PAUSED"` 且 `paused = false` 时：

- 「暂停全关」不命中（要求 `paused == true`）；
- 所有状态迁移规则被排除（`phase` 不匹配 `FILLING`/`CIRCULATION`/…）。

→ **零规则命中**，输出字段全空 → 调用方输出校验报 `C2 返回值缺少字段` → 触发**故障兜底全关**并标记任务失败。

### 4.2 影响面

在**当前调用方实现下该组合不可达**（调用方暂停时直接短路、不调用规则引擎）。因此属**健壮性缺口**：换调用方、或后续把暂停改为走引擎，就会出现"规则集无输出 → 误判故障 → 任务 FAILED"。

### 4.3 需求描述

优先采用 **S1-a**：

| 方案 | 说明 | 评价 |
|---|---|---|
| **S1-a（推荐）** | 规则集新增一条 **最低 salience** 的兜底规则，条件 `nextPhase == null`，动作输出 `PAUSED` + 全关 + 明确 reason | 不枚举阶段，**任何"零命中"输入都有确定输出**；依赖 R5 的包装类型能力 |
| S1-b | 兜底条件写成 `phase == "PAUSED"` | 只覆盖这一种残留态，其他零命中组合仍无输出；不推荐 |
| S1-c | 不加规则，改在契约层声明"`phase=PAUSED` 时必须同时传 `paused=true`"，并在调用方校验 | 零规则改动，但把健壮性责任推给每个调用方 |

**salience 注意事项**（平台实测语义）：高 salience **先**执行、低 salience **后**执行，且**后写覆盖**。因此兜底规则必须给**最低** salience，才能在任何正常规则命中时被覆盖、仅在无人写 `nextPhase` 时生效。

**caveat**：`nextPhase == null` 的判据是"本次执行没有任何规则写过 `nextPhase`"。若将来出现"命中但故意不写 `nextPhase`"的规则，该判据会误触发。当前规则集约定"每条命中规则都写 `nextPhase`"，故成立；如需更强语义，建议平台提供显式的"未命中"标记（可归入 P3）。

### 4.4 验收标准

| # | 验收项 | 判定 |
|---|---|---|
| S1-1 | 传入 `phase=PAUSED, paused=false` 时规则集有确定输出 | 输出 `PAUSED` + 全关，不触发故障兜底 |
| S1-2 | 正常迁移场景下兜底规则**不**生效 | 输出与既有行为一致 |
| S1-3 | 兜底规则的 salience 最低 | 任何正常规则命中时覆盖兜底结果 |
| S1-4 | 既有 19 条套件用例全绿 | 无回归 |
| S1-5 | 若选 S1-c，则调用方校验落地并有测试 | 缺 `paused` 时调用方拒绝发送 |

## 5. 责任划分与实施顺序

### 5.1 责任划分

| 需求 | 平台 | 项目侧（demo / 中控适配器） |
|---|---|---|

### 5.2 建议实施顺序

| 顺序 | 内容 | 理由 |
|---|---|---|
| 1 | **P2 语义确认**（客户拍板甲/乙/丙） | 阻塞 P1 的参数集合与 S1 的兜底逻辑；安全缺陷优先级最高 |

| 4 | **S1 兜底规则** | 改动小，消除"零命中→误判故障" |
| 5 | **P3 参数管理** | 通用能力，可随平台迭代排期 |
